## 1. Footnotes don't work in Calibre or on Kindle Paperwhite

**Symptom.** A footnote link jumps to the start of the chapter (the test book
has a single chapter, so it looks like it jumps "to the whole text"). The
footnote text itself is not visible anywhere in the book.

**What's in the EPUB** (`~/Documents/Повелитель тайн (v1).epub`,
`OEBPS/c-dvnfo5e0.xhtml`):

```html
<p>
  … Чжоу Минжуй <sup><a epub:type="noteref" href="#fn-1">1</a></sup> …
</p>
<aside epub:type="footnote" id="fn-1">
  <p>Прим. ред.: …</p>
</aside>
```

`theme.css`: `aside[epub|type~="footnote"] { display: none; }`.

**Causes.**

1. **`display: none` on `aside`.** This was a deliberate spec decision
   ("Kindle shows them as pop-ups", spec §5 / line ~626, AGENTS.md
   section 5), but it is wrong for real readers:
   - the footnote text is never shown, hence "the note itself is nowhere";
   - during conversion (Calibre → AZW3/MOBI, Send to Kindle → KFX) hidden
     elements and their anchors can be lost. Then the link goes to the start
     of the file, and Calibre's pop-up shows the whole chapter document.
2. **No back link.** The `noteref` has no `id`, and the footnote has no link
   back. Kindle Publishing Guidelines require bidirectional links for
   pop-up footnotes. Without a back link, once the reader has jumped to the
   footnote, the only way back is the "back" button.
3. **The footnote sits in the middle of the text**, right after the paragraph
   (where the author defined it). If it is made visible, it will break up the
   text. The usual practice is a footnote block at the end of the chapter (or
   a separate notes.xhtml).

Code: `src/assets/epub/theme.css.ts` (the `display:none` rule),
`src/services/epub/chapter.ts` (AST walk and rendering via
`renderToHTML({ xhtmlMode: true })`; `footnoteDef` nodes stay in place in
the block flow), the custom.css template `src/assets/epub/custom.css.ts`
(comment about `aside`).

**Proposed fix (draft).**

- Remove `display: none`.
- In `renderChapter`, pull all `footnoteDef` nodes out of the block flow and
  output them at the end of the chapter in a separate block
  (`<section epub:type="footnotes">` or `<hr/>` + `aside`s), styled with a
  small font.
- Make links bidirectional: `noteref` gets `id="fnref-N"`, and a number link
  `<a href="#fnref-N">N</a>` is added at the start of the footnote.
  `renderToHTML` in novlang-js can't do this, so either post-process the
  XHTML after rendering (via DOM; it is already parsed for the well-formed
  check), or open an issue/PR in novlang-js for an option.
- The app preview already shows footnotes at the bottom (`div.footnote-def`);
  bring it to the same scheme (number, back link).
- Fix the spec (§5, theme.css) and AGENTS.md.
- Verification: epubcheck + manual check in Calibre viewer, Calibre → AZW3,
  and Send to Kindle on a Paperwhite (add an item to
  `docs/release-checklist.md`).

**User's delivery path (answer):** Calibre "Send to device", which converts
EPUB → MOBI by itself. So the main target path is the Calibre converter
(MOBI/AZW3), not Amazon KFX.

- MOBI/AZW3 has no `epub:type`. Kindle firmware shows a footnote as a pop-up
  if the link target contains a link back to the reference point (the
  bidirectional-link heuristic). So item 2 (back links) is key, not
  cosmetic.
- The Calibre converter apparently drops a hidden `aside` together with its
  anchor → the link goes to the start of the file. Check on the fixed build.
- A possible recommendation for the README/help: choose AZW3 in Calibre
  instead of the old MOBI (Preferences → Behavior → preferred output
  format). Test the fix in both formats.

**Decision: all footnotes go at the end of the book** (user's answer).
Refined scheme:

- A separate file `OEBPS/notes.xhtml`, last in the spine, only if the book
  has at least one footnote. `<section epub:type="endnotes">`, footnotes are
  `aside
epub:type="endnote"` (or `footnote`; check which survives Calibre
  conversion better).
- A "Notes" heading in the book's language (`services/epub/labels.ts`), an
  entry in nav/ncx and landmarks.
- Inside, footnotes are grouped by chapter: a subheading with the chapter
  title (linking to the chapter), followed by that chapter's footnotes.
- ids are unique per book: `fn-<chapterId>-<id>` and `fnref-<chapterId>-<id>`.
  Link in the text: `notes.xhtml#fn-…`, back link: `c-<chapterId>.xhtml#fnref-…`.
- Numbering: author labels (`[^1]`) repeat in every chapter. Options: keep
  the labels as-is within the per-chapter groups, or use continuous
  numbering across the book. Tentatively: continuous (unambiguous and
  independent of labels); decide when writing the plan.
- Multiple references to one footnote: back link to the first one (or one per
  reference). Minor; decide in the plan.
- Risk: cross-file links must work through Calibre conversion (they usually
  do); pop-ups on Kindle need manual checking.
- The app preview shows one chapter: there footnotes stay at the bottom of
  the chapter; just add back links and consistent number styling.

## 2. Export to a Kindle format (AZW3)

**Request.** Add export directly to a format Kindle Paperwhite can read.

**Facts.**

- Paperwhite reads AZW3 (KF8), MOBI, KFX, PDF, TXT. It doesn't read EPUB over
  USB, but Send to Kindle accepts EPUB and converts it to KFX itself (since
  2022 Amazon has removed MOBI from Send to Kindle).
- Old MOBI (MOBI6) has worse CSS support. The target should be AZW3.
- Amazon stopped supporting KindleGen in 2020, and it can't be
  redistributed. Not an option.
- This revisits the original decision "Output — EPUB". Reason: the user
  delivers books through Calibre, which is an extra conversion step.

**Options.**

- **A. Our own AZW3 writer in TS.** PalmDB + MOBI/EXTH headers, KF8
  skeleton/fragment, NCX indexes, PalmDoc compression, image records. Scope
  comparable to the whole EPUB build; the format is poorly documented
  (reference: `calibre/ebooks/mobi/writer8`), and it can only be verified on
  a device. High risk, not for the next iterations.
- **B. Call `ebook-convert` from an installed Calibre (recommended).**
  Build the EPUB as now → temp file → `ebook-convert in.epub
out.azw3 --output-profile kindle_pw3` → result to disk. The user already
  has Calibre installed (`/Applications/calibre.app/Contents/MacOS/ebook-convert`).
  - Auto-detection: standard paths on macOS / Windows (`C:\Program
Files\Calibre2\ebook-convert.exe`) / Linux (`/usr/bin`, `/opt/calibre`)
    - PATH; a "Path to ebook-convert" field in Settings.
  - If Calibre isn't found, the AZW3 format in ExportDialog is disabled with
    a hint and a link to calibre-ebook.com.
  - Rust command `convert_with_calibre(epub_bytes, out_path, profile)`:
    `tauri-plugin-shell` is a poor fit because the path is user-defined
    (the shell plugin's scope is static). Timeout, cancellation, stderr to
    the log and into the error text (`AppError`).
  - Downside: external dependency; conversion takes seconds.
- **C. Add nothing, documentation only.** In the README/help:
  "Calibre → Preferences → Behavior → preferred format AZW3", or
  Send to Kindle with EPUB. Zero code, but the step remains.

**What else to consider for B.**

- ExportDialog: EPUB / AZW3 format choice (remembered in settings); the file
  name extension changes.
- Footnotes (issue 1) should be checked on the actual `ebook-convert`
  output: a CI step "EPUB → AZW3 → `ebook-convert out.azw3 out.epub`" can be
  added as a smoke test that footnote anchors survived conversion.
- Copying to the device over USB / sending to Kindle is still out of
  scope (the "file to disk only" decision stands).

**Open questions.**

- Is option B (dependency on an installed Calibre) acceptable?

### 2a. What Paperwhite 3 (7th generation, 2015) and Paperwhite 12th generation (2024) support

|                  | Paperwhite 3 (2015)                                      | Paperwhite 12 (2024)        |
| ---------------- | -------------------------------------------------------- | --------------------------- |
| Reads directly   | AZW3 (KF8), AZW, DRM-free MOBI, PRC, TXT, PDF            | same                        |
| KFX              | yes (store books and Send to Kindle; firmware 5.8+)      | yes                         |
| EPUB             | no; only via Send to Kindle (Amazon converts) or Calibre | same                        |
| Screen           | 6″, 1072×1448, 300 ppi, b/w                              | 7″, 1264×1680, 300 ppi, b/w |
| Pop-up footnotes | yes (AZW3/KFX, bidirectional links required)             | yes                         |

Takeaways for the project:

- No format differences between the models. The common denominator is
  **AZW3**; old MOBI isn't needed.
- The "Kindle Paperwhite" image preset (1264×1680) matches the newer
  model's screen; for PW3 images are slightly larger than the screen, which
  is fine, the reader will scale them down. A separate PW3 preset isn't
  needed.
- Both models are b/w: the "grayscale" option is useful for reducing size.
- Calibre "Send to device" picked MOBI because of the format order in the
  Kindle driver settings / preferred output format. This is configurable in
  Calibre; the app's help should suggest putting AZW3 first.

## 3. Cover in Metadata: huge height, narrow width

**Symptom.** The cover thumbnail in `CoverPicker` is stretched to a huge
height, squeezed in width, and cropped on the sides.

**Cause** (`src/components/metadata/CoverPicker.vue:50-56`):

```vue
<AspectRatio :ratio="1600 / 2560" class="w-32 overflow-hidden rounded-lg bg-muted">
  <img … class="h-full w-full object-cover" />
</AspectRatio>
```

reka-ui's `AspectRatio` renders two wrappers: an outer
`position: relative; width: 100%; padding-bottom: N%` and an inner
`position: absolute; inset: 0`, and **`class` (`$attrs`) goes to the
inner one**. Result:

- the outer wrapper takes the full card width, and height = card
  width × 1.6 (hence "huge height");
- the inner one gets `w-32` (128 px) and stretches to that height
  (hence "narrow");
- `object-cover` crops the image on the sides to fill the narrow, tall
  rectangle.

Additionally: the aspect ratio is hardcoded as 1600/2560, while the real
cover may differ — `object-cover` will crop it too.

**Fix.**

- Constrain the width on a **wrapper** around `AspectRatio`
  (`<div class="w-32">…</div>`), or drop `AspectRatio` altogether and
  use `<img class="w-32 h-auto">` / `aspect-[5/8]`.
- `object-contain` instead of `object-cover` so the cover isn't cropped;
  take the ratio from the real dimensions (`imageDimensions`, as in
  `ImageView`).
- A component test for the markup (size set on the outer container).

**Along the way (same place, minor):**

- `ImageView.vue:55` uses `AspectRatio` correctly (class without width,
  width constrained by `max-w-2xl`), but a tall image in it ends up
  ~1000 px high. Worth limiting with `max-h` (e.g. `max-h-[70vh]`).
- Next to the "Recommended 1600×2560" hint we could show the cover's actual
  dimensions and warn if it is noticeably smaller.
- The "Drop an image here" zone is separate from the thumbnail. The whole
  card or the thumbnail itself could be the drop target.

## 4. No syntax highlighting in the custom.css editor

**Symptom.** CSS in the `custom.css` editor is shown in a single color.

**Cause** (`src/components/editor/CssEditor.vue`). The `css()` extension from
`@codemirror/lang-css` is enabled; it parses CSS and assigns tags, but
**doesn't set colors**. Colors come from `syntaxHighlighting(HighlightStyle)`.
Usually `basicSetup` does this (`defaultHighlightStyle`), but it isn't used
here, and a custom style was added only for NovLang
(`novlangHighlightStyle` in `SourceEditor.vue:70`). There is no style for CSS.

**Fix.**

- A custom `cssHighlightStyle` (e.g. in `editor-theme.ts` or
  `css-language.ts`) with tag colors for the light and dark themes:
  selectors / classes, properties, values and numbers with units, strings,
  comments (muted), at-rules (`@namespace`, `@media`),
  `!important`. Colors via theme CSS variables, as for NovLang, so that
  theme switching works without recreating the editor.
- Also add what `basicSetup` provides that is missing here and matters for
  CSS: `bracketMatching`, `closeBrackets`, `indentOnInput`, autocompletion
  (`@codemirror/autocomplete` + `cssCompletionSource`, which already exists
  in `lang-css`), `highlightActiveLine`, search (Mod+F — `searchKeymap`,
  `@codemirror/search` is already a dependency), `foldGutter` — optional.
- Test: an `EditorState` with the extension has `syntaxHighlighting` for CSS
  (or a snapshot of token classes in the view).

Images"):

**Decisions (user's answers).**

- **Inserting an image into the text — only via the "Image" button on the
  formatting toolbar (item 5).** The "Insert into text" action is removed
  from the gallery. (Proposal for the plan: the toolbar button opens a menu
  "From file…" / "From book…", where the latter is a compact gallery in a
  Popover; this allows inserting an already imported image.)
- **Multi-select + bulk delete** — in v1. Selection: Mod+click,
  Shift+click (range), Mod+A, Esc — clear; a checkbox on the tile on
  hover / in selection mode. Deletion: one confirmation with a list
  (and the chapters where the images are used) + one UndoToast that undoes
  everything at once.
- **Bulk rename** (new; the spec previously said "No renaming"): for the
  selected images, enter a new name → files become
  `НОВОЕ-ИМЯ_ИНДЕКС.<расширение>` (NEW-NAME_INDEX.<extension>) **in
  selection order** (not grid order). Each file's extension is preserved.

What to consider for renaming:

- Store the selection order explicitly (an array, not a Set); a
  Shift+click range adds in grid order. Show a number on the tile (①②③) in
  selection mode so the order is visible before applying.
- Dialog: name field, "before → after" preview for each file, conflict
  warning.
- Rewrite all references: `![](images/old.jpg)` in all chapters,
  `metadata.cover`, `url(images/…)` in custom.css. This is a single book
  mutation (`services/book/renameResources`, pure function + tests) and one
  UndoToast. Chapters are changed via `EditorState` transactions (like
  search replace), so that Mod+Z in a chapter also works.
- Conflicts: if `new_3.jpg` already exists and isn't in the selection — an
  error in the preview; permutations within the selection (a→b, b→a) are
  done via temporary names.
- ⚠ Name sanitizing (`utils/paths.ts`, `normalizeResourceName`) currently
  keeps only `[a-zA-Z0-9]` and replaces everything else with `-`:
  - the `_` in the `ИМЯ_ИНДЕКС` (NAME_INDEX) format would be replaced with
    `-` — allow `_`;
  - Cyrillic and Chinese characters are **removed entirely** (the name
    "Повелитель" would become `image`). Transliteration is needed (at least
    ru → latin), or Unicode must be allowed in names. For Kindle/Calibre
    compatibility, ASCII + transliteration is safer. Also affects import.

**Decisions on renaming and selection (user's answers).**

- **The index** is zero-padded to the number of digits in the count of
  selected images: up to 9 → `1…9`, 10–99 → `01…99`, 100–999 → `001…999`,
  etc. (width = `String(count).length`).
- **Allowed name characters — only Latin letters, digits, and a couple of
  symbols (`_`, `-`).** The restriction is applied right at input: the field
  doesn't accept other characters (a `beforeinput`/`input` filter + a hint
  below the field), no transliteration. Bring `normalizeResourceName` in
  `utils/paths.ts` to the same set (allow `_`). **Case — lowercase** (as
  now): input is converted to lowercase.
- **Press-and-hold selection (like the Android gallery):**
  - a long press (~400–500 ms, mouse or finger) on a tile selects it and
    enters selection mode; after that a regular click toggles tile
    selection;
  - if, without releasing, you move to another tile — **everything from the
    first pressed tile to the tile under the cursor** is selected (a range
    in grid order); moving back shrinks/flips the range around the same
    anchor tile;
  - the rename order within such a range runs from the anchor tile in the
    direction of movement;
  - implemented with Pointer Events (`pointerdown` + timer,
    `pointermove` + `elementFromPoint`/`setPointerCapture`), with
    grid auto-scroll near the top/bottom edge; not via HTML5 DnD (that
    remains for dragging files into the gallery);
  - keep the keyboard/mouse alternatives: Mod+click, Shift+click,
    Mod+A, Esc.
