# User feedback — 2026-10-04

A cumulative list of issues: symptom, cause, possible solution. We will build
a work plan from it later.

## 1. Preview stays light under the dark app theme

**Symptom.** With the dark theme (or "system" on a dark OS) the whole window
is dark, but the preview pane is a bright white page. It is glaring next to
the dark editor. Wanted: a dark preview in the colours of old paper, a quick
way back to the real look, and a clear sign that the preview is styled.

**Cause.** This is deliberate, not a regression:

- `src/components/editor/PreviewPane.vue` — the `<iframe>` has a hard-coded
  `class="bg-white"`; the comment says the EPUB styles "assume a light page",
  so the preview stays "paper-white under the dark theme".
- `styles()` in the same file builds the frame CSS from `themeCss` +
  preview-only rules + `previewCss` + `custom.css`. None of it knows the app
  theme: no `color-scheme`, no text/background colours, and the notes
  separator is a hard-coded `border-top: 1px solid #ddd`.
- `useResolvedTheme()` (`src/composables/use-theme.ts`) already gives the
  resolved `"light" | "dark"`, and the CodeMirror editors already follow it
  (`editor-theme.ts`). The preview is the only part that doesn't.

**Constraint.** `theme.css` goes into the EPUB and must stay colourless:
Kindle and other readers set their own colours, and hard-coded colours break
their night mode. So the dark palette and image dimming are **preview-only**,
like `preview.css`.

**Decisions (user, 2026-10-04).**

- Palette: **dark old paper** (warm brown-sepia), not Monokai.
- A toggle in the **top-right corner of the preview** turns the styled look
  off and shows the original (theme.css + custom.css on white).
- A **separate toggle** for dimmed images.
- While the preview is styled, the **status bar** says the preview does not
  reflect what the book will look like.

**Possible solution.**

1. **Palette — derived from the app's dark theme.** The preview should look
   like part of the app, with only a light paper warmth on top (user,
   2026-10-04: bring the preview towards the app theme, not the other way
   round; the app theme is not changed).

   The iframe can't see the parent's CSS variables, so `PreviewPane` reads
   the resolved app tokens (`getComputedStyle(document.documentElement)`:
   `--background`, `--foreground`, `--muted-foreground`, `--border`, `--ring`)
   and injects them into the frame as `:root { --app-bg: …; … }`, re-injected
   when the theme changes. New `src/assets/epub/preview-dark.css.ts` (preview
   only, never in the EPUB) builds on them:

   | Element                                  | Colour                                                                                         |
   | ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
   | page background                          | `color-mix(in oklch, var(--app-bg) 90%, #8a6a3a)` — app background with a faint paper warmth   |
   | body text                                | `color-mix(in oklch, var(--app-fg) 88%, #e8d9b5)` — app text, slightly cream                   |
   | `h1`, endnotes section `h2`              | warm accent, e.g. `oklch(0.80 0.06 80)` (dull gold)                                            |
   | `a.noteref`, `a.endnote-backlink`, links | same accent family, a bit darker, e.g. `oklch(0.72 0.08 70)`                                   |
   | `blockquote`                             | `var(--app-muted-fg)`; left rule inherits it (item 7)                                          |
   | `p.novlang-scene-break`                  | `var(--app-muted-fg)`                                                                          |
   | notes separator, borders                 | `var(--app-border)`                                                                            |
   | text selection                           | `color-mix(in oklch, var(--app-ring) 45%, transparent)` — as in the editor (`editor-theme.ts`) |

   Plus `:root { color-scheme: dark; }` so the frame's scrollbars go dark.
   Exact mix ratios are tuned by eye; the warmth must stay subtle enough that
   the preview sits next to the editor without a visible seam. Serif font as
   now. Since the colours come from tokens, any later change to the app's
   dark palette carries over to the preview automatically.

2. **Image dimming.** `preview-dim-images.css.ts`:
   `img { filter: brightness(.8) sepia(.15); }` — white illustrations stop
   glaring and sit closer to the paper tone. Only when dark styling is on
   (there's nothing to dim on white).

3. **Toggles in the preview corner.** A small overlay in the top-right
   corner of `PreviewPane` (outside the iframe, `absolute` over it), two
   icon toggle buttons (shadcn `Toggle`, tooltip + `aria-pressed`):
   - "Paper style" (e.g. `IconPalette` / `IconSun`) — off = original look;
   - "Dim images" (e.g. `IconPhotoOff` / `IconContrast`) — disabled while
     paper style is off.
     Shortcut **Mod+Alt+P** toggles paper style (free today; added to
     `useShortcuts` and to the shortcut list in Settings, if there is one).
     Shown only under the dark theme (under the light theme the preview is the
     original anyway; the shortcut does nothing there). Semi-transparent until hovered, so it doesn't cover the
     text. Both states live in app settings (`settingsStore`:
     `previewPaperStyle`, `previewDimImages`, default on), shared by all books
     like the other layout settings — not in `.edb`.

4. **`PreviewPane.vue` wiring.** `styles()` gets the resolved theme + the two
   flags and appends the layers. The existing `watchEffect(renderPreview)`
   rewrites `<style data-preview>` on change, no frame reload. The frame
   background follows (the same mixed paper colour, set on the iframe via a
   class/inline style, vs `bg-white`) so there's no white flash before the
   frame document loads. The `#ddd` separator moves into the palette (light
   `#ddd`, dark `var(--app-border)`).

5. **Order relative to `custom.css`.** Paper layer goes _before_
   `custom.css`, so the user's rules still win. Downside: hard-coded dark
   text colours in `custom.css` become unreadable on the dark page — exactly
   the case where the "original look" toggle helps. Add a line to the
   `custom.css` template: "most e-ink readers ignore colours; switch the
   preview to its original look to check them".

6. **Status bar notice.** `StatusBar.vue` (full-width footer, left side next
   to `WarningsPopover`): when the preview is visible (mode Split/Preview)
   and paper style is on, show a muted label with an icon, e.g.
   «Превью стилизовано — книга будет выглядеть иначе» /
   "Styled preview — not how the book will look". Clicking it switches the
   preview to the original look. Hidden in Text mode and when the style is
   off. New keys in ru/en/zh-CN.

7. **Tests.**
   - `PreviewPane`: dark theme → `style[data-preview]` has the paper palette;
     paper off → only theme + custom; dim on/off adds/removes the `img`
     filter; no iframe recreation on toggle; toggles hidden under light theme.
   - `StatusBar`: notice shown/hidden by mode + flag; click turns style off.
   - `buildEpub`: output contains neither paper nor dim rules.
   - Settings store: new flags persist; locale key parity.

**Resolved questions.**

- App theme stays as is; the preview palette is derived from it (see 1).
- Shortcut: yes, Mod+Alt+P (see 3).

## 2. Tab in the CSS editor leaves the editor instead of accepting a hint

**Symptom.** In the `custom.css` editor the autocomplete pop-up appears, but
pressing Tab doesn't accept the suggestion: focus jumps to the splitter
between the editor and the preview. Tab also can't be used to indent.

**Cause.** Tab isn't bound to anything in the CSS editor, so the browser's
default Tab behaviour (move focus to the next focusable element) wins, and
the next one is the splitter in `ResizableSplit`.

- `src/components/editor/css-language.ts` — `cssEditingExtensions()` adds
  `autocompletion()` with `completionKeymap`. In CodeMirror that keymap
  accepts a completion with **Enter** only; Tab is deliberately not in it.
- `src/components/editor/CssEditor.vue` — its keymap is
  `preserveOpenShortcutKeymap + defaultKeymap + historyKeymap`. `defaultKeymap`
  doesn't bind Tab either; `indentWithTab` from `@codemirror/commands` is
  opt-in and not used.

**Possible solution.**

1. In `cssEditingExtensions()` put a Tab binding **before**
   `completionKeymap` (higher precedence):
   `{ key: "Tab", run: acceptCompletion }` from `@codemirror/autocomplete`.
   `acceptCompletion` returns `false` when no pop-up is open, so Tab falls
   through to the next binding.
2. Then `indentWithTab` (`Tab` → `indentMore`, `Shift-Tab` → `indentLess`)
   from `@codemirror/commands`, so Tab without a pop-up indents instead of
   leaving the editor. Expected order in the keymap:
   `Tab→acceptCompletion`, then `indentWithTab`.
3. **Keyboard escape hatch (a11y).** Once Tab is captured, a keyboard user
   needs a way out of the editor. CodeMirror 6 has it built in: **Escape,
   then Tab** moves focus (and `Mod-m` toggles "tab focus mode"). Document it
   in the shortcut list / a tooltip; nothing to implement.
4. **Tests** (`CssEditor.test.ts`, through `EditorView` in happy-dom or the
   commands on `EditorState`): with an open completion, Tab inserts the
   selected item; without one, Tab indents the line and focus stays in
   `.cm-content`; Shift-Tab un-indents.

**Not affected / to decide.** The NovLang `SourceEditor`
(`SourceEditor.vue`) has no autocompletion and is prose, where indentation
is meaningless (paragraph indent comes from CSS). Tab moving focus there is
acceptable; leave it as is unless it also bothers the user.

## 3. Chapter search: "all" button is useless, a match count is missing

**Symptom.** In the chapter search panel (Mod+F) the "all" button just
selects every match (multi-cursor). For a novel editor that's practically
useless. What's actually missing is how many matches there are — a
"Count" button instead of "all".

**Cause.** The panel is CodeMirror's stock one, unconfigured:

- `src/components/editor/SourceEditor.vue` and `css-language.ts` bind
  `Mod-f` → `openSearchPanel` + `searchKeymap`; `FormatToolbar.vue` calls
  `openSearchPanel` too. There is no `search({ … })` config, so
  `@codemirror/search`'s default panel is used: field, next / previous /
  **all** (`selectMatches`), checkboxes match case / regexp / by word,
  replace / replace all. It has no match counter at all.
- Only colours are adapted (`editor-theme.ts`, `.cm-panel …`).
- Side findings in the same panel:
  - **not localized** — no `EditorState.phrases` anywhere, so the panel is
    in English under RU / zh-CN UI;
  - **"by word" differs from book search** — CodeMirror's whole-word test
    uses its own word-char definition, while the sidebar search
    (`src/services/search/query.ts`, `compileQuery`) uses
    `(?<![\p{L}\p{N}_])…(?![\p{L}\p{N}_])`. The same query can give
    different results in Mod+F and Mod+Shift+F.

**Possible solution.**

1. **Own panel via `search({ createPanel })`** (`@codemirror/search`
   supports a custom panel; the search state, `SearchQuery`,
   `findNext`/`findPrevious`/`replaceNext`/`replaceAll` stay CodeMirror's).
   New `components/editor/chapter-search-panel.ts` (plain DOM, like the
   stock panel, or a mounted small Vue component) shared by `SourceEditor`
   and `CssEditor`. Contents:
   - field, ↑ / ↓ (previous / next), Aa / word / `.*` toggles in the same
     style and with the same icons as the sidebar search (`SearchView`);
   - **match counter** instead of "all";
   - replace field, "Replace", "Replace all";
   - texts from vue-i18n (ru / en / zh-CN) — fixes localization.
     "Select all matches" isn't removed as a command: it stays on the keyboard
     (`Alt-Enter` in the field, as in `searchKeymap`) for those who want it.

2. **Count: live counter rather than a button (recommended).** Like VS Code
   — «3 из 17» / "3 of 17" next to the field, updated on every query change
   and on moving between matches; «Нет результатов» / "No results" in a muted
   / warning colour; «Ошибка в regex» for an invalid pattern. A button makes
   the user click to get a number that can just be visible. If a button is
   still preferred — "Count" shows «17 вхождений» until the query changes.
   - Counting: iterate `query.getCursor(state)` (or `compileQuery` over the
     doc, see 3), debounced ~100 ms, capped (e.g. "1000+") so a one-letter
     query on a 300 KB chapter doesn't stall typing.
   - Current index: position of the main selection among the matches.

3. **One matcher for both searches.** Make "by word" (and case / regex)
   identical in Mod+F and Mod+Shift+F: either give CodeMirror's
   `SearchQuery` a regexp built by `compileQuery` (regex mode with the
   `\p{L}` boundaries), or count/highlight through `services/search/find.ts`
   and use CodeMirror only for selection and replacement. Prefer the first:
   less code, CodeMirror's highlighting keeps working.

4. **Tests.** Panel: counter "k of N" for a known doc; updates on query and
   option change; "No results"; invalid regex; cap. `wholeWord` parity test:
   the same query on the same text gives the same matches through the
   chapter panel and through `services/search`. Locale key parity.

**Decision (user, 2026-10-04).** All four points accepted: own panel,
**live counter «3 из 17»** (no "Count" button), one matcher for both
searches, tests as listed.

## 4. Preview text runs to the very bottom edge

**Symptom.** At the end of a chapter the last line of the preview sits right
at the bottom edge of the pane, with no space under it.

**Cause.** `src/assets/epub/preview.css.ts`:
`body { max-width: 36em; margin: auto; }`. `margin: auto` sets **all four**
margins to `auto`, and vertical `auto` margins of a block in normal flow
compute to `0`. That also removes the browser's default 8 px body margin. So
the body has no space at the bottom; the last `p` has `margin: 0`
(`theme.css`), and the text touches the edge. Top looks fine only because
the chapter usually starts with `h1 { margin: 1em 0 }`. The same rule gives
**zero side space** when the pane is narrower than 36em — text touches the
left/right edges too.

For comparison, `SourceEditor.vue` gives `.cm-content` `padding: 1rem`, so
the source has room around it and the preview doesn't.

**Possible solution.**

1. `preview.css.ts`:
   `body { max-width: 36em; margin: 0 auto; padding: 1.5em 1.5em 4em; }`
   — horizontal centring stays, plus a top/side gutter and a larger bottom
   gutter. `preview.css` is preview-only, the EPUB is unaffected (readers
   set their own margins).
2. Bottom size — **decision (user, 2026-10-04): fixed, ~4em.** Options
   that were considered:
   - **fixed, ~4em (recommended):** the last line sits comfortably above
     the edge; the proportional scroll sync stays almost exact;
   - **"scroll past end", e.g. `padding-bottom: 50vh`:** the last line can
     be scrolled up to the middle of the pane, like `scrollPastEnd()` in
     editors. Then the source editor should get `scrollPastEnd()` too,
     otherwise the proportional sync drifts at the end (preview scrolled
     to the bottom = a half-empty pane while the source is only at its end).
3. Check the `custom.css` interplay: a user `body { margin/padding }` rule
   still wins (custom.css comes last) — that's fine, the preview should show
   their CSS.
4. **Test.** `PreviewPane` test: `style[data-preview]` contains the body
   padding; visual check in Split and Preview modes, narrow pane (< 36em)
   and with endnotes at the end of the chapter (`section.preview-notes` is
   the last element then).

## 5. Metadata: can't choose an image already in the book as the cover

**Symptom.** An image was added to the gallery, but in Metadata → Cover
there's no way to pick it. Only a new file from disk can become the cover.

**Cause.**

- `src/components/metadata/CoverPicker.vue` — the only actions are
  "Choose…" (`onPick`) and drop of an external file (`onDropFile`).
- `src/views/EditorView.vue`, `pickCover()` → `files.pickImage()` (OS file
  dialog) → `importCover()` → `imageImport.importFile(…)` →
  `setCover(book, result.path)`. So the cover always goes through an
  **import from disk**. Picking the same file again would work only thanks
  to SHA-256 dedup (no duplicate is created), but the user has to find the
  original on disk — and an image pasted from the clipboard
  (`pasted-…png`) has no original at all.
- Setting a cover from the book's images exists only in the gallery
  **context menu** (right click on a tile → "Set as cover",
  `ImageGallery.vue` `contextAction` → `setCover`). Not discoverable: no
  button, not in the selection bar, not in `ImageView`
  (`components/editor/ImageView.vue` has no cover action at all).
- The pieces for a picker already exist: `ImagePickerPopover.vue` (grid of
  the book's images, used by "Insert image" in the format toolbar) and
  `setCover` in `services/book/metadata`.

**Possible solution.**

1. **CoverPicker: "Choose…" → two sources.** Turn the button into a
   dropdown / popover:
   - «Из изображений книги» / "From book images" — `ImagePickerPopover`
     (reused; current cover highlighted, tiles get `aria-pressed`); pick →
     `setCover(book, path)`, no import. Hidden or disabled with a hint when
     the book has no images;
   - «Из файла…» / "From file…" — current `pickCover()`.
     Or simpler: the popover itself shows the book's images plus a
     "From file…" tile/button at the end. Drop onto the card stays as is.
2. **ImageView: "Set as cover" button** next to the image info (and
   «Обложка» badge / disabled state when it already is the cover).
3. **Gallery: make the action visible.** "Set as cover" in the selection
   bar when exactly one image is selected (next to "Rename…"), not only in
   the context menu.
4. `ImagePickerPopover` gets an optional `selected?: string` prop for the
   highlight; the format-toolbar usage is unchanged. Consider a
   cover-oriented aspect (`aspect-[5/8]`, `object-contain`) in cover mode so
   a cover isn't judged by a square crop.
5. **Tests.** `CoverPicker`: picking a book image calls `setCover` with its
   path and doesn't call `pickImage`/import; empty book → option disabled
   with hint. `ImageView`: button sets the cover / is disabled for the
   current cover. Gallery selection bar: action present only for a single
   selection. Setting the cover marks the project dirty, like other
   metadata edits.

## 6. Renaming a single image adds a number suffix

**Symptom.** Gallery → select one image → "Rename…" → type `cover` → the
image becomes `cover_1.jpg`, not `cover.jpg`. The `_NN` numbering only makes
sense for a batch rename (spec §9.4: names `<name>_<NN>.<ext>` for a
**batch**).

**Cause.** There is only one naming rule, and it always numbers:

- `src/services/book/rename-resources.ts`, `planBatchRename()`:
  `to = images/${name}_${String(index + 1).padStart(width, "0")}${ext}` for
  every selection size, including 1 (`width = 1` → `_1`).
- `src/components/images/RenameImagesDialog.vue` repeats the same formula in
  its own `preview` computed (duplicated logic — preview and actual result
  can drift apart), and always opens with an empty name field.
- Entry points (`ImageGallery.vue`): selection bar "Rename…" and tile context
  menu → `renaming = selection.order` or `[path]` — a single image goes
  through the same batch path.
- The spec line "Rename is in scope since 2026-10-03 (batch only…)" was
  read literally as "always the batch rule"; renaming one image was never
  specified separately.

**Possible solution.**

1. **`planBatchRename` → `planRename`**: one image → `images/<name><ext>`
   (extension kept), two or more → `<name>_<NN><ext>` as now. Conflict
   check unchanged (a single target equal to another existing file →
   "`cover.jpg` already exists"); renaming to its own current name → empty
   plan, Confirm disabled.
2. **Dialog derives its preview from the plan** (`plan.renames`, or the
   from-list with "—" while the name is empty / invalid) instead of its own
   formula — no second source of truth.
3. **Single-image UX:** title «Переименовать изображение» / "Rename image"
   instead of the batch title; the field is **prefilled with the current
   name without extension** and selected, so a small edit is easy; the
   preview line is just `old.jpg → new.jpg`. Batch keeps an empty field and
   the numbered list.
4. "Rename…" in `ImageView` too (single image), reusing the same dialog.
5. **Spec.** Update §9.4 (and the AGENTS.md 4b note): "one image →
   `<name>.<ext>`; several → `<name>_<NN>.<ext>`".
6. **Tests.** `rename-resources`: single → no suffix; single to own name →
   no renames; single conflict; batch unchanged (padding, selection order,
   swaps). Dialog: single opens prefilled, preview matches plan; batch preview
   matches plan.

**Decision (user, 2026-10-04).** All six points accepted, including
"Rename…" in `ImageView`.

## 7. Block quotes have no visual style in the book

**Symptom / wish.** A `> quote` only gets wider side margins, so in the book
it barely differs from a normal paragraph. Wanted: a visible style in the
base book theme, e.g. a rule on the left.

**Current state.**

- `src/assets/epub/theme.css.ts`: `blockquote { margin: 1em 2em; }` — nothing
  else. This file goes into the EPUB (`OEBPS/theme.css`) and into the preview.
- NovLang renders `> …` as `<blockquote><p>…</p></blockquote>`, one
  `blockquote` per quote block. The quote's first `p` already has no indent
  thanks to `p:first-child { text-indent: 0 }`; following paragraphs inside
  the quote keep the 1.5em indent.
- Theme rule from the spec (§5): no fixed fonts, sizes **or colours**, so the
  reader's night mode and e-ink rendering keep working.

**Options.**

- **A. Left rule (recommended, the user's suggestion).**

  ```css
  blockquote {
    margin: 1em 0 1em 1em;
    padding-left: 1em;
    border-left: 0.2em solid;
  }
  ```

  No border colour on purpose: the CSS2 initial `border-color` is the text
  colour, so the rule is black on paper and turns light in night mode
  together with the text — no hard-coded colour, no `currentColor` (whose
  support on older Kindle firmware is uncertain). The right margin goes to
  0 so the narrow Kindle column isn't squeezed from both sides. Borders are
  supported in KF8/AZW3 and KFX; only legacy MOBI7 drops them, and the quote
  then falls back to an indented block — acceptable.

- **B. Italic + indent:** `blockquote { margin: 1em 1.5em; font-style:
italic; }` (with `blockquote em { font-style: normal; }` so emphasis
  inside still stands out). Classic for epigraphs and letters, but long
  italic passages are tiring to read on e-ink.
- **C. Classic book block quote:** indent on both sides + slightly smaller
  text (`font-size: 0.95em`). Conflicts with the "no font sizes" rule in
  the theme (it's relative, but still a size), so not preferred.

**Possible solution (with A).**

1. `theme.css.ts`: replace the `blockquote` rule with option A. Consider
   `blockquote + p { text-indent: 0; }` too, like after a heading or a scene
   break: text right after a quote often continues the same thought — to
   decide.
2. **Dark preview (item 1).** The paper palette doesn't need a separate
   border colour: the rule follows the text colour automatically. The
   `var(--app-border)` entry for the quote's left rule in item 1's table is
   dropped (the quote text colour `var(--app-muted-fg)` is enough; the rule
   inherits it).
3. **`custom.css` template** (`custom.css.ts`): mention `blockquote` styling
   as an override example (e.g. switching to italic, option B).
4. **Spec.** Update §5 theme.css bullet: "blockquote — left rule without a
   colour (inherits the text colour), padding instead of a right margin".
5. **Checks.** epubcheck (CSS stays valid); visual check in the preview
   (light and dark), Kindle Previewer / Calibre viewer, and on the
   Paperwhite with night mode on.

**Decision (user, 2026-10-04).** Option A (left rule without a colour) and
points 1–5 accepted. Still open: `blockquote + p { text-indent: 0; }`
(default if not decided: keep the indent, i.e. no extra rule).

## 8. Top-left corner shows the file path instead of the book title

**Symptom.** The file-menu button in the top-left corner shows the full path
of the `.edb` file (e.g. `/Users/…/Documents/My novel.edb`). It's long, gets
truncated, and isn't what the user thinks of as "the project". Wanted
(user, 2026-10-04):

1. show the **book title** from Metadata → «Название» there (no new
   "Project" item — the user first suggested one, then dropped it);
2. if the title is still the default when the book is saved for the first
   time, take it from the chosen **file name**;
3. don't show the path; add **«Показать в папке» / "Show in folder"** to the
   same menu (where Save is).

**Cause.**

- `src/views/EditorView.vue`: `<FileMenu :title="project.filePath ??
t('editor.unnamedBook', 'Untitled book')" …>` — the path is passed as the
  label on purpose.
- `src/components/layout/FileMenu.vue`: groups New / Open · Save / Save as ·
  Close project. No reveal command.
- New book title is a localized placeholder (`services/book/create.ts`:
  «Без названия» / "Untitled" / «未命名»). First save → `saveAs()` in
  `src/composables/use-project-files.ts` proposes
  `projectFileName(title)` → «Без названия.edb»; if the user types another
  file name, the title stays «Без названия» and the book is exported with
  that title.
- The opener service already has `reveal(path)` (`services/platform/opener.ts`,
  `revealItemInDir`), used by the export notification; the `opener:default`
  capability covers it.

**Possible solution.**

1. **Label = book title.** `FileMenu :title="project.book?.metadata.title ||
t('editor.unnamedBook', 'Untitled book')"`. Reactive, so editing
   «Название» in Metadata updates the corner immediately. The "•" for unsaved
   changes stays. The full path is not shown anywhere in the header (no
   tooltip either).
2. **Title from the file name on first save.** In `saveAs()` (only when
   `project.filePath` was `null`, i.e. the book has never been saved): if
   the title is empty or equals one of the default placeholders
   (`«Без названия»`, `"Untitled"`, `«未命名»` — export them from
   `create.ts` as a list, e.g. `DEFAULT_TITLES`, instead of comparing to
   strings in two places), set it to the chosen file's base name without
   `.edb` via `updateMetadata` **before** `project.save(target)`, so the new
   title goes into the same write. Regular Save, Save as of an already saved
   book, and a title the user typed are never touched. Recovery sessions
   restored as "never saved" behave the same.
3. **«Показать в папке» in `FileMenu`.** New command `reveal`, in the Save

   `services.opener.reveal(project.filePath)`; an error → the usual
   `platform.opener` error notification, as in `use-export.ts`. Label per OS
   is optional ("Show in Finder" / "Show in Explorer" / "Show in folder");
   one neutral label «Показать в папке» is enough for v1. New locale keys in
   ru / en / zh-CN.
4. **Welcome / recent files are unchanged** — they still show paths, which is
   where the path is useful.
